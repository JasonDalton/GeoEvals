# Data governance

This document states how GeoEvals handles licenses, attribution, restricted data and privacy.
It applies to every dataset, fixture and benchmark in the repository, and to data that users
download themselves.

## Licenses

| What | License |
| --- | --- |
| Code (`src/`, `tests/`, scripts) | MIT ([`LICENSE`](../LICENSE)) |
| JSON Schemas and benchmark specs | MIT |
| Synthetic fixtures written or generated by the GeoEvals contributors | MIT, as recorded in each benchmark's `manifest.yaml` |
| Third-party data | Its own license, recorded per asset in a dataset manifest |

A dataset that is publicly accessible is not necessarily openly licensed or redistributable.
Before an asset is used, read the provider's terms. This applies especially to
OpenStreetMap-derived data, imagery, mobility data, POI data, census data and human-made
labels.

The [license inventory](../datasets/README.md#license-inventory) lists every asset of every
manifest with its license, attribution, redistributable flag and the benchmark that uses it.
It is generated by `geoevals data inventory`, and CI fails if the committed table is out of
date.

Runtime dependencies must be compatible with the MIT license. CI runs `geoevals data licenses`,
which writes [`dependency-licenses.md`](dependency-licenses.md) and fails on a GPL or AGPL
runtime dependency (LGPL and permissive licenses are allowed).

## Dataset manifests

Every data asset that a benchmark uses is listed in a dataset manifest that matches
[`schemas/dataset-manifest.schema.json`](../schemas/dataset-manifest.schema.json). A
manifest is YAML (`assets:` list) or JSONL (one asset per line). Each asset records:

| Field | Meaning |
| --- | --- |
| `asset_id` | A unique ID within the manifest |
| `path` | The local file, relative to the manifest |
| `source_url` or `citation` | Where the data comes from |
| `access_date` | When it was downloaded or created |
| `license`, `attribution` | The license (an SPDX ID where one exists) and the attribution it requires |
| `redistributable` | Whether the file may be committed and shipped with GeoEvals |
| `sha256` | The checksum of the file |
| `crs`, `bbox`, `time_range` | The spatial and temporal metadata |
| `processing_steps` | Every step from the source to this file |
| `split` | The benchmark split the asset belongs to |
| `known_limitations` | What the data does not represent well |

Check a manifest and its files:

```sh
uv run geoevals validate benchmarks/gis_correctness/manifest.yaml
uv run geoevals data verify benchmarks/gis_correctness/manifest.yaml   # ok, missing or checksum_mismatch per asset
```

Every run records the SHA-256 of the benchmark's manifest (`dataset_manifest_hash`), and the
report lists the license and attribution of every asset.

## Restricted data

Data with `redistributable: false` is referenced, never committed:

- Its manifest is committed, with the source, license, checksum and processing steps, so the
  data can be downloaded again and checked.
- The file itself goes into the gitignored `data/raw/`. `geoevals validate` fails if a
  non-redistributable asset is tracked in git or sits in a path that git would commit.
- A script downloads it. `geoevals data fetch <dataset_id>` writes the file, a local manifest
  with the real access date and checksum, and a `fetch.json` record into `data/raw/<id>/`. It
  refuses to write into a tracked path. Instructions for each dataset are in
  [`datasets/download_instructions/`](../datasets/download_instructions/).
- Data derived from restricted data stays in `data/raw/` too. For example,
  `geoevals bench build human_context_pilot` writes the pilot benchmark, which is built from
  an OpenStreetMap extract, into `data/raw/human_context_pilot/benchmark/`.

OpenStreetMap data is licensed under the ODbL-1.0 and must be attributed as
"© OpenStreetMap contributors". A database derived from it can carry share-alike
obligations, so v0.1 commits no OSM-derived data. Only synthetic fixtures are committed.
Whether small derived samples may ever be committed is an open question for a qualified
reviewer.

## Fixtures in the repository

- Keep fixtures small: under 1 MB per benchmark.
- Prefer synthetic data. A generator script that is seeded and deterministic (for example
  `benchmarks/human_context/make_fixture.py`) is better than a binary file nobody can rebuild.
- List every fixture in the benchmark's `manifest.yaml` with its checksum. When a fixture
  changes, update its `sha256` (`shasum -a 256 <file>`), or `geoevals data verify` fails.
- Do not commit rasters outside `tests/fixtures/` (`.gitignore` excludes `*.tif`).

## Secrets and personal data

Never commit:

- API keys, access tokens, passwords or `.env` files (`.env` and `.env.*` are gitignored)
- precise personal location traces
- sensitive operational data

Adapters that call paid or hosted services must read credentials from the environment, never
from a committed config file. CI uses no secrets.

CI scans the full git history with [gitleaks](https://github.com/gitleaks/gitleaks) and fails
on any finding. A secret that reaches a commit stays in the history: revoke it first, then
rewrite the history. To scan locally before you push, run `gitleaks git .` from the repository
root.

## Mobility, activity and demographic data

Before such data is used in a benchmark:

- Verify how it was aggregated, the consent and usage restrictions, the minimum cohort size
  and the risk of re-identification.
- Use only aggregated demographics, and apply minimum aggregation thresholds where needed.
- Report errors by group where the data allows it, and document possible disparate impact.

The human-context pillar tags every value as `observed`, `proxy` or `judgment`, and makes no
claims about social relationships inferred from co-location, mobility proxies or
demographics. See [`human-context.md`](human-context.md#what-the-benchmark-does-not-claim).

## Dataset cards

Each benchmark has a card (`README.md` in its directory) that covers its purpose, how the data
was collected or generated, the geography, the time range, the schema, the licenses, the
limitations and the intended and prohibited uses, each under its own `##` heading: Purpose,
Collection process, Geography, Time range, Schema, License, Limitations, Intended uses and
Prohibited uses. `tests/test_dataset_cards.py` fails if a benchmark directory has no card or a
card lacks one of these headings. See
[`benchmarks/gis_correctness/README.md`](../benchmarks/gis_correctness/README.md),
[`benchmarks/human_context/README.md`](../benchmarks/human_context/README.md) and
[`benchmarks/smoke/README.md`](../benchmarks/smoke/README.md).
